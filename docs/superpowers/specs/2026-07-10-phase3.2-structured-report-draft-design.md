# Phase 3.2 Structured Report Draft Design

## Goal

Generate one deterministic, auditable intermediate report artifact at `draft/report_draft.json` from the existing Phase 3.1 outline and Phase 2 evidence layer. The artifact supports later report production without generating Markdown, Word, PowerPoint, PDF, images, or UI changes.

## Boundaries

Phase 3.2 reads only:

- `draft/report_outline.json`
- `research/search_plan.json`
- `research/sources.json`
- `research/research_notes.json`
- `research/source_review.json`
- task metadata already present in the current task record

Phase 3.2 writes only `draft/report_draft.json`. It never modifies Phase 2 artifacts, `draft/report_outline.json`, task input files, or an earlier report draft in place. Every run reconstructs the complete draft from current upstream inputs and atomically replaces the previous output.

Phase 3.2 does not call a model, an external API, a database, browser search, Chrome/CDP, or any new network capability. It does not generate final report prose or formal delivery files.

## Architecture

Add `backend/services/report_drafter.py` as the Phase 3.2 boundary. It owns tolerant input loading, source normalization, current-review reconciliation, outline-to-section conversion, block construction, source-index construction, validation, and atomic persistence.

`backend/services/task_runner.py` invokes the drafter immediately after `generate_report_outline`. The report-producing legacy workflow remains downstream and unchanged. `outline_only` remains unchanged because it does not produce the Phase 2 and Phase 3.1 inputs required by the drafter.

Extend the existing artifact metadata registry in `backend/services/phase2_records.py` with exactly one entry for `draft/report_draft.json`. The existing generic recursive file list and download routes remain unchanged.

## Output contract

The root is a JSON object with this stable contract:

```json
{
  "schema": "phase3.report_draft.v1",
  "task_id": "task identifier",
  "title": "report title",
  "status": "draft",
  "outline_schema": "phase3.report_outline.v1",
  "sections": [],
  "source_index": [],
  "provenance": {
    "outline_path": "draft/report_outline.json",
    "research_inputs": [
      "research/sources.json",
      "research/research_notes.json",
      "research/source_review.json"
    ],
    "included_source_keys": [],
    "excluded_source_keys": [],
    "input_warnings": [],
    "generation_mode": "deterministic",
    "generated_at": "timestamp"
  },
  "warnings": []
}
```

`schema` is the sole report-draft schema field. `status` is always `draft`; the artifact never implies final-report status. The Phase 3.1 schema remains unchanged and is copied into `outline_schema` when available.

## Section model

Every valid outline section produces exactly one draft section in the original outline order:

```json
{
  "section_id": "section-001",
  "outline_section_id": "1",
  "order": 1,
  "title": "Background and Scope",
  "purpose": "background",
  "status": "draft",
  "content_blocks": [],
  "supporting_sources": [],
  "source_keys": [],
  "needs_manual_review": true,
  "warnings": []
}
```

`outline_section_id` copies the actual Phase 3.1 `section_id`; Phase 3.2 does not invent a second outline identity. `section_id` is a deterministic output-local ID derived only from the 1-based valid-section order. A malformed section is skipped with an input warning, while other valid sections retain their relative order.

An outline with `sections: []` produces a draft with `sections: []`. A valid section with no usable evidence remains present with empty `content_blocks`, empty source collections, `needs_manual_review: true`, and a structured warning. It never receives placeholder prose.

## Content block model

Version 1 supports only `paragraph` blocks. Each usable source produces at most one independent block:

```json
{
  "block_id": "section-001-block-001",
  "order": 1,
  "block_type": "paragraph",
  "text": "Existing source-derived text",
  "claim_type": "factual",
  "supporting_sources": [],
  "source_keys": [],
  "needs_manual_review": false
}
```

Block IDs depend only on section and block order. No UUID or random value is used.

Text selection is conservative and deterministic, in this order:

1. matching `research_notes.json` `preliminary_note`;
2. matching research-note `snippet`;
3. matching research-note `claim_supported`;
4. matching `sources.json` `snippet`;
5. matching `sources.json` `claim_supported`.

Titles, URLs, and synthesized labels are not factual block text. Text receives whitespace normalization and a fixed maximum length only; numbers, units, technical names, negations, and dates are not inferred or rewritten. Multiple sources produce multiple blocks rather than an unauditable merged paragraph.

## Review policy

Phase 3.2 reuses Phase 2 review status values and Phase 3.1 stable-key matching. It does not define a new review parser.

- `approved`: eligible for a block with `claim_type: factual` and `needs_manual_review: false`.
- `unreviewed`: eligible only when already linked by the Phase 3.1 outline; produces `claim_type: candidate` and `needs_manual_review: true`.
- `rejected`: excluded from blocks, section source collections, and `source_index`; its stable key is recorded in `provenance.excluded_source_keys`.
- `needs_followup`: excluded using the same body-content rule as Phase 3.1 and recorded as excluded.
- missing or invalid review status: normalized to `unreviewed`, matching the established Phase 2/3.1 behavior.

The drafter starts from each outline section's `supporting_sources`; it never introduces a source that the outline did not link. It then rechecks current Phase 2 review state so a source changed to `rejected` after outline generation cannot re-enter the draft.

## Stable source matching and deduplication

Sources are reconciled using the existing Phase 2 `source_review_key` algorithm and indexed by both stable `source_key` and `source_id`, with stable-key matches taking precedence. The output requires a non-empty stable `source_key` for every block source.

Within each section, duplicate source references are removed by `source_key` while preserving first outline-reference order. Section-level sources are the stable union of actual block sources. Root `source_index` contains only sources used by at least one block and is ordered by first use across section and block order.

`used_by_sections` and `used_by_blocks` are stable, order-preserving, deduplicated arrays.

## Provenance and warnings

Each supporting-source object retains:

- `source_key`
- `source_id` when available
- `title`
- `url`
- `review_status`
- text provenance identifying the input artifact and field used

Root provenance records the outline path, research input paths, included and excluded stable keys, tolerant input warnings, deterministic generation mode, and generation time.

Warnings are structured objects with stable `code`, `artifact`, optional section/source identity, and a human-readable `message`. They never contain Python tracebacks, exception objects, or absolute local filesystem paths.

## Invalid-input degradation

Missing, empty, malformed, null, scalar, or list-valued `report_outline.json` produces a legal empty draft with an input warning. Missing or malformed Phase 2 inputs are replaced with conservative empty objects and recorded in input warnings.

Invalid individual sections or sources are skipped without discarding other valid records. Missing source matches, missing stable keys, unusable text, rejected sources, and outline references to absent sources never produce blocks. Affected sections remain with empty or reduced blocks and structured warnings.

No input failure writes a traceback into the artifact or leaves the task permanently running. Output validation occurs before atomic persistence.

## Determinism and atomic replacement

Section order comes only from the outline array. Block and source order comes only from first valid outline-reference order. Dictionaries and sets are never serialized as ordering sources. Every identifier is ordinal and deterministic.

Repeated execution ignores the previous `report_draft.json`, rebuilds from current inputs, and atomically replaces the target. Except for `provenance.generated_at`, equivalent inputs produce equivalent JSON semantics and ordering.

Atomic writing uses a same-directory temporary file, UTF-8 JSON, flush, `fsync`, close, and `os.replace`, followed by best-effort temporary cleanup. No `.tmp` file remains after success.

## File-list and download compatibility

Add one metadata definition:

- `relative_path`: `draft/report_draft.json`
- `file_type`: `report_draft`
- `category`: `phase3_draft`
- `description`: `Structured report section draft derived from reviewed research artifacts`

The generic task-file list discovers the artifact recursively. Existing safe download routes return it without a dedicated endpoint. No frontend change is required.

## Workflow behavior

For `research_only`, task step 4 generates research notes, report outline, and report draft, then preserves existing skips for document production. For report-producing task types, report draft generation occurs after report outline generation and before the legacy writer. Phase 3.2 does not block on external systems and does not modify upstream artifacts.

When upstream inputs are unavailable, the workflow still writes a legal empty draft rather than failing solely because Phase 3.2 has no usable content.

## Testing strategy

Create `backend/tests/test_phase3_report_draft.py` covering:

- approved and unreviewed block semantics;
- exact outline-section inheritance and empty-outline behavior;
- rejected/follow-up revalidation and exclusion provenance;
- no-text sources producing no block;
- stable-key matching, duplicate-key removal, and source-index reverse links;
- missing, malformed, scalar, and partially corrupt inputs;
- absent outline source references;
- deterministic ordering under reordered Phase 2 records;
- repeat execution equivalence excluding `generated_at`;
- atomic replacement with no temporary residue;
- unchanged hashes for Phase 2 artifacts and `report_outline.json`;
- workflow creation, file metadata, generic listing, and download compatibility.

Regression verification includes the complete backend test directory, existing frontend history/reload tests, Python compilation, JavaScript syntax, live `/health` and `/api/health`, real file download, temporary-port release, and confirmation that no Word, PowerPoint, PDF, Markdown report, image, or UI file was generated or modified.
