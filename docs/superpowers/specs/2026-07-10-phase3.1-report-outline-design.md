# Phase 3.1 Report Outline Design

## Goal

Convert the existing Phase 2 evidence artifacts and task metadata into one traceable report-planning artifact at `draft/report_outline.json`. Phase 3.1 does not generate report prose, slide plans, figures, PPT, Word, images, or UI features.

## Scope and constraints

- Read only existing `research/search_plan.json`, `research/sources.json`, `research/research_notes.json`, `research/source_review.json`, and task metadata.
- Do not query external databases or invoke a model to invent or expand findings.
- Preserve every Phase 2 file path, schema, and behavior.
- Generate only `draft/report_outline.json`.
- Create `draft/` when absent.
- Replace an existing outline atomically on rerun.
- Do not modify the UI unless the current generic file list cannot display the new artifact.

## Architecture

Add `backend/services/report_planner.py` as a deterministic Phase 3 planning boundary. It owns input loading, review-state filtering, section construction, provenance construction, validation, and atomic JSON writing. `backend/services/task_runner.py` invokes the planner after research notes are available and before any later writer or document-generation behavior. Existing Phase 2 helpers remain responsible only for evidence-layer artifacts.

The current recursive task file listing and safe download endpoint remain the transport mechanisms. File metadata is extended with one stable draft artifact definition so `draft/report_outline.json` is returned with `relative_path: draft/report_outline.json`, `file_type: report_outline`, and a draft-planning category. No second name is introduced for this artifact type.

## Data flow

1. Load all four JSON inputs from the task workspace and task metadata from the current `TaskRecord`.
2. Index `sources.json` by `source_id` and stable review identity.
3. Index active `source_review.json` entries by `source_key` and `source_id`; stale entries do not support sections.
4. Join normalized sources with research-note source groups and search-plan query purposes.
5. Apply review policy before deriving any section or key point.
6. Group eligible sources by query purpose in search-plan order and create one section for each non-empty group.
7. Validate that every section has at least one supporting source and that every supporting source resolves to an eligible source.
8. Write the complete payload to a same-directory temporary file, flush it, and atomically replace `draft/report_outline.json`.

## Review policy

- `approved`: eligible and preferred. These sources determine section confidence and review status when present.
- `unreviewed`: eligible only as explicitly risky candidate evidence. Sections containing any such source are marked for review and cannot receive high confidence.
- `rejected`: ineligible for section titles, purposes, key points, figures, or supporting sources.
- `needs_followup`: ineligible for body content and added to `missing_information` with its source identity and review note.
- Missing or invalid review states are treated as `unreviewed`, matching the existing Phase 2 review normalization.
- If no `approved` or `unreviewed` active sources exist, output a valid outline with `sections: []` and a corresponding `missing_information` entry.

## Output contract

The output retains the requested top-level structure and adds explicit schema and provenance fields without changing Phase 2 contracts:

```json
{
  "schema_version": "phase3.report_outline.v1",
  "task_id": "",
  "generated_at": "",
  "title": "",
  "objective": "",
  "audience": "",
  "sections": [
    {
      "section_id": "1",
      "title": "",
      "purpose": "",
      "key_points": [],
      "supporting_sources": [
        {
          "source_id": "",
          "source_key": "",
          "title": "",
          "url": "",
          "review_status": "approved",
          "provenance": [
            {
              "artifact": "research/sources.json",
              "record_id": "",
              "field": "snippet"
            }
          ]
        }
      ],
      "figures_needed": [],
      "confidence": "",
      "review_status": ""
    }
  ],
  "recommended_figures": [],
  "missing_information": [],
  "generation_notes": "",
  "provenance": {
    "inputs": [
      "research/search_plan.json",
      "research/sources.json",
      "research/research_notes.json",
      "research/source_review.json",
      "state/status.json"
    ]
  }
}
```

`title` and `audience` come from task metadata. `objective` is a bounded planning statement derived from task title, type, domain, and audience, not a research conclusion. Section titles and purposes come from existing search-plan query purposes. Each key point is copied or conservatively labeled from a source title, snippet, claim-supported text, or research-note preliminary note; it is never expanded into a new factual claim.

`confidence` uses one stable set of string values: `high`, `medium`, `low`. A section is `high` only when all support is approved and the sources contain usable note text; mixed approved/unreviewed support is `medium`; unreviewed-only or weak-text support is `low`. `review_status` is `approved` only when all support is approved, otherwise `needs_review`.

`figures_needed` and `recommended_figures` may contain only figure needs already present in task input or research artifacts. They remain empty when no input artifact requests a figure.

## Workflow integration

For `research_only`, generate the outline immediately after `summarize_phase2_research` and then preserve the existing skip behavior for later document-production steps. For report-producing task types, generate it inside the existing research-and-write step after research summarization and before the legacy writer is called. `outline_only` currently does not have research notes and therefore is not changed in Phase 3.1.

Missing, malformed, or non-object input JSON is recorded in `provenance.input_warnings` and replaced with conservative empty fallback data. Missing evidence must never create an untraceable placeholder section; when no usable evidence remains, the planner writes a valid outline with `sections: []`.

## File metadata and download compatibility

Add a single metadata rule for `draft/report_outline.json`:

- `relative_path`: `draft/report_outline.json`
- `file_type`: `report_outline`
- `category`: `phase3_draft`
- `description`: structured report outline derived from reviewed research artifacts

The generic recursive file list already discovers files under `draft/`. The existing download endpoint already resolves returned `file_id` values under the storage root, so no new endpoint or UI path is required. Tests will prove both behaviors.

## Testing

Create `backend/tests/test_phase3_report_outline.py` with focused tests for:

- approved-source section generation and complete provenance;
- approved preference and unreviewed risk marking;
- rejected-source exclusion;
- needs-followup transfer to `missing_information`;
- zero eligible sources producing `sections: []`;
- automatic `draft/` creation and atomic rerun replacement;
- file metadata and recursive task-file discovery using `report_outline` as the sole file type;
- end-to-end workflow creation of `draft/report_outline.json` from existing Phase 2 inputs.

Regression verification includes `test_phase2_source_review.py`, `test_task_history.py`, the existing frontend restore/history tests, and live `/health` plus `/api/health` checks. No PPT, Word, image, or additional draft artifact is created during Phase 3.1 verification.
